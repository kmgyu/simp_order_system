# Review Change Skill

## 1. 목적 및 적용 범위

PR·커밋·작업 트리의 변경을 **정확성·회귀 위험·보안·성능·테스트 충분성** 기준으로 평가한다. 코드 리뷰 요청은 기본적으로 **읽기 전용**이다. 수정 요청이 따로 있지 않으면 코드를 변경하지 않는다.

## 2. 리뷰 절차

1. 비교 기준(대상 브랜치/커밋)과 변경 목적을 확인한다.
2. `git diff`와 주변 코드를 읽고 영향받는 호출자/데이터 계약을 추적한다.
3. 정상·오류·경계 조건, 예외 처리, 권한/입력 검증, 동시성, 데이터 정합성 영향을 확인한다.
4. API/DB/이벤트가 바뀌면 소비자 호환성·배포 순서·롤백을 확인한다.
5. 테스트 커버리지의 **내용**을 평가한다. 단순 테스트 개수로 품질을 판단하지 않는다.
6. 문제를 심각도 순으로 정리하고 근거·재현 조건·수정 제안을 제시한다.

## 3. 지적 항목 형식

```text
[SEVERITY] 제목
- 위치: <파일 경로:라인 (확인 가능한 경우)>
- 근거: <실제 코드/동작에서 확인한 사실>
- 영향: <오류, 보안, 호환성, 성능 등>
- 권고: <최소 수정 또는 추가 테스트>
```

| 등급 | 의미 |
| --- | --- |
| BLOCKER | 데이터 손실·심각한 보안 문제·배포 불가 수준 |
| HIGH | 핵심 기능 오류·중요한 회귀 가능성 |
| MEDIUM | 특정 조건의 오류·성능/운영 위험 |
| LOW | 국소적 가독성·유지보수성 개선 |

## 4. 리뷰 결과

- 먼저 **검증된 주요 문제**를 중요도 순으로 제시한다.
- 명확한 문제가 없다면 `확인된 문제 없음`이라고 쓰되, 검토하지 못한 범위를 적는다.
- 검증된 사실과 잠재적 우려/가설을 구분한다.
- 가능하면 테스트 명령과 재현 절차를 제시하되, 실행하지 않았다면 실행했다고 주장하지 않는다.
- 개선 방향이 큰 변경이면 별도 작업으로 제안하고 현재 PR에 무단 반영하지 않는다.
