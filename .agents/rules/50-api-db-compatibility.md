# API·DB·데이터 계약 호환성 규칙

## 1. 목적 및 적용 범위

API, DB, 데이터 계약에 영향을 주는 변경에서 소비자 호환성·정합성·무중단 배포 가능성을 검토한다. 일반적인 UI 텍스트 수정 등 관련 없는 작업에는 적용하지 않아도 된다.

## 2. API·이벤트 계약

- **MUST**: 요청/응답/이벤트 구조를 변경하기 전에 현재 소비자와 실제 계약을 확인한다.
- **MUST NOT**: 승인 없이 사용 중인 필드 제거, 필수화, 의미 변경, 오류 코드 변경 등 비호환 변경을 한다.
- **SHOULD**: 비호환 변경이 필요하면 새 계약 도입 → 소비자 전환 → 기존 계약 제거 순서를 검토한다.
- 입력 검증, 오류 응답, 페이지네이션, 재시도, 멱등성 등의 변경은 기존 클라이언트 영향을 확인한다.
- 계약/문서/테스트를 함께 갱신한다.

## 3. DB 및 마이그레이션

- **MUST**: 실제 DB 엔진·버전·트랜잭션·락 특성을 확인한다. 특정 DB 전용 명령을 근거 없이 적용하지 않는다.
- **MUST**: 기존 데이터 크기, DDL 잠금, 인덱스 영향, 저장 공간, 롤백 가능성을 평가한다.
- **MUST**: 무결성/제약 조건 변경 시 기존 데이터의 위반 여부를 확인할 방법을 제시한다.
- **MUST NOT**: 승인 없이 데이터 삭제, 테이블 교체, 마이그레이션 실행, 운영 DB 접속을 진행하지 않는다.
- **SHOULD**: 무중단 요구가 있으면 호환되는 스키마 확장 → 데이터/애플리케이션 전환 → 정리(expand–migrate–contract)를 우선 검토한다.
- **SHOULD**: 실패 후 재실행 가능성, 데이터 백필, 롤백 전략 및 관측 항목을 문서화한다.

## 4. 성능과 정합성

- 쿼리 최적화는 실제 데이터 분포·인덱스·실행계획·측정 환경을 바탕으로 판단한다. 가상 통계를 사실로 보고하지 않는다.
- 동시성 변경에는 트랜잭션 경계, 중복 요청, 격리 수준, 락 경합, 재처리 가능성을 검토한다.
- 이벤트/비동기 처리 변경에는 메시지 중복, 순서, 실패 재처리, 멱등성을 확인한다.

## 5. 변경 보고 기준

변경한 계약, 영향받는 호출자, 마이그레이션 순서, 테스트, 모니터링 포인트, 롤백 방안을 보고한다. 내용을 모르면 `미확인`으로 표시한다.
