# 보안 및 데이터 보호 규칙

## 1. 목적 및 적용 범위

기능 개발·디버깅·테스트 중 기밀 유출, 과도한 권한, 파괴적 작업, 외부 부작용을 방지한다.

## 2. 비밀 정보와 개인정보

- **MUST NOT**: 인증 키, 토큰, 비밀번호, 실제 개인정보를 소스·테스트 데이터·커밋 메시지·PR 본문·로그에 저장하거나 출력하지 않는다.
- **MUST**: 설정은 프로젝트 표준 비밀 관리 방식 또는 환경 변수로 주입한다. `*.example` 파일에는 더미값과 변수명만 기록한다.
- **MUST**: 로그·오류 응답·추적 이벤트에는 비밀 정보가 포함되지 않는지 확인한다.
- **MUST NOT**: 문제 해결에 불필요한 개인 파일·인증 저장소·운영 자격 증명을 열람하지 않는다.
- **SHOULD**: 개인정보는 최소 수집·최소 권한·보관 기간 등 프로젝트 정책을 따른다.

## 3. 애플리케이션 보안

- 입력 경계에서 검증하고 DB 호출에는 지원되는 바인딩/매개변수화 질의를 사용한다.
- 인증(authentication)과 인가(authorization)를 구분한다. 서버 측에서 객체 단위 접근 권한도 확인한다.
- 외부 HTTP 호출/파일 업로드/경로/명령 실행 시 인젝션, SSRF, 경로 탐색, 리소스 사용 제한을 검토한다.
- 웹 서비스에서는 사용 중인 인증 방식에 적합한 CSRF/XSS/CORS 대책을 확인한다. 무조건 모든 Origin을 허용하지 않는다.
- 의존성의 새 권한, 패키지 출처, 취약점 영향은 변경 시 검토한다.

## 4. 위험 작업의 승인 게이트

아래 작업은 **영향 범위·대상 환경·복구 방법을 먼저 제시하고 명시적인 사용자 승인을 받는다.**

- 데이터 `DROP`/대량 `DELETE`/일괄 갱신, 파괴적 마이그레이션
- 운영/공유 DB 또는 외부 서비스를 대상으로 하는 쓰기 요청
- 스테이징/운영 배포, 서비스 설정 변경, 비용 발생 가능 명령
- `git reset --hard`, 강제 푸시, 대규모 파일/브랜치 삭제
- 접근 제어·권한·방화벽 정책 변경

동의 없는 대체 작업(예: 테스트 DB가 없으니 운영 DB 사용)도 금지한다.

## 5. 사고/오류 발견 시

- 토큰 유출이 의심되면 값을 재노출하지 말고 **종류·노출 위치·필요한 폐기/교체 작업**을 안전하게 설명한다.
- 보안 결함을 발견하면 기존 코드 변경 여부와 관계없이 위험도·재현 조건(비밀 제거)·권고 조치를 보고한다.
- 로그/화면 캡처/출력에서 민감 정보를 마스킹한다.

## 6. 검증 기준

- diff에 비밀 정보나 실제 개인정보가 포함되지 않는가?
- 외부 입력·권한·데이터 파괴 가능성을 검토했는가?
- 승인하지 않은 고위험 명령/외부 쓰기/배포가 수행되지 않았는가?
