# 개발 컨벤션

## 1. 목적 및 적용 범위

언어와 프레임워크에 관계없이 유지보수성·가독성·일관성을 높이는 최소 공통 기준을 적용한다. 프로젝트별 기술 스택과 실행 명령은 `docs/PROJECT_CONTEXT.md`에 기록한다.

## 2. 코드 작성 원칙

- **MUST**: 저장소에 이미 존재하는 아키텍처, 패키지 경계, 명명 규칙, formatter, linter를 우선한다.
- **MUST**: 새로운 코드의 책임을 명확히 한다. UI/라우팅·비즈니스 규칙·데이터 접근의 책임이 섞이지 않도록 기존 구조를 존중한다.
- **MUST**: 기존 동작을 바꾸지 않는 요청에서 공개 인터페이스, 데이터 모델, 설정값을 불필요하게 바꾸지 않는다.
- **MUST**: 변경 이유를 파악하지 못한 기존 코드를 제거하지 않는다.
- **SHOULD**: 한 함수는 명확한 작업을 수행하도록 유지하고, 중복은 이해 가능한 단위로 추출한다. 과도한 추상화는 피한다.
- **SHOULD**: 하드코딩된 정책 값, 매직 넘버, 환경별 경로를 의미가 있는 상수/설정으로 분리한다.
- **MUST NOT**: 미사용 추상화, 예상만으로 만든 확장 포인트, 불필요한 새 라이브러리를 도입하지 않는다.

## 3. 명명·스타일

| 대상 | 기본 원칙 |
| --- | --- |
| 변수·함수 | 의미와 역할을 드러내는 이름. 해당 언어의 관례를 따름 |
| 클래스·타입 | 역할을 나타내는 명사. 기존 네이밍을 유지 |
| 상수 | 변경 불가능한 정책 값임을 표현. 언어 표준 스타일 사용 |
| 파일·디렉터리 | 기존 구조·명명 방식 유지. 새 파일은 내용이 유추되는 이름 |
| 주석 | **무엇을 하는지**보다 **왜 이렇게 해야 하는지** 설명 |
| 문서·로그 | 민감 정보 제외. 요구사항, 제약, 디버깅 맥락이 드러나도록 작성 |

언어별 스타일 차이(예: Python `snake_case`, JavaScript/TypeScript `camelCase`)는 프로젝트의 실제 관례와 포매터를 따른다. 스타일 규칙을 맞추기 위한 대량 파일 재포맷은 별도 승인을 받는다.

## 4. 예외·오류 처리

- **MUST**: 입력 경계(API, CLI, 파일, 메시지, 사용자 입력)에서 유효성을 검증한다.
- **MUST**: 예상 가능한 실패와 예기치 않은 오류를 구분하고, 숨기지 않는다.
- **MUST**: 예외를 포착한 경우 적절히 처리·전파·기록한다. 실패한 작업을 성공으로 반환하지 않는다.
- **MUST NOT**: 인증 정보, 결제 정보, 개인정보, 내부 스택 트레이스 등 민감 정보를 외부 응답으로 노출하지 않는다.
- **SHOULD**: 재시도에는 중복 실행 위험, 횟수 제한, 백오프, 타임아웃을 고려한다.

## 5. 데이터·계약·의존성

- 외부 API·데이터베이스 스키마·메시지 포맷을 변경할 때는 호환성 영향과 소비자를 확인한다.
- 의존성 추가/업그레이드는 기존 도구로 해결할 수 없는지 확인하고 목적·보안·운영 영향을 설명한다.
- 시간·통화·숫자 정밀도·문자 인코딩은 도메인 규칙과 기존 계약을 따른다. **임의로 기준을 선택하지 않는다.**
- 데이터를 영속화하는 로직은 중복 요청, 트랜잭션 경계, 실패 시 정합성을 검토한다.

## 6. 문서화와 변경 범위

- README/설정/실행 명령/API 계약에 영향을 준 변경은 관련 문서도 함께 수정한다.
- TODO/FIXME는 가능한 한 이유·후속 조치·관련 이슈를 포함한다. 임의의 완료 시점은 약속하지 않는다.
- 요청과 무관한 버그나 개선점을 발견했어도 별도 항목으로 보고하고 묶어서 수정하지 않는다.

## 7. 검증 기준

- 기존 패턴/포매터/린터와 일치하는가?
- 변경 범위가 요구사항에 한정되었는가?
- 오류·경계 입력·데이터 정합성에 대한 처리가 적절한가?
- 관련 테스트·문서가 갱신되었는가?
