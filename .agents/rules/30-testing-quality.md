# 테스트 및 품질 검증 규칙

## 1. 목적 및 적용 범위

코드 수정 시 실제 검증 가능한 근거를 확보한다. 테스트 프레임워크 및 실행 명령은 `docs/PROJECT_CONTEXT.md`의 확인된 내용을 사용한다.

## 2. 테스트 작성 원칙

- **MUST**: 버그 수정 시 가능하면 해당 문제를 재현하는 회귀 테스트를 추가한다.
- **MUST**: 기능 추가·동작 변경 시 정상 입력과 중요한 실패/경계 조건을 검증한다.
- **MUST**: 테스트에는 관찰 가능한 결과를 검증하는 의미 있는 assertion이 있어야 한다.
- **MUST**: 실행하지 않았거나 실패한 테스트를 통과했다고 말하지 않는다.
- **MUST NOT**: 테스트 실패를 해결하기 위해 검증 자체를 제거·무력화·무분별하게 스킵하지 않는다.
- **SHOULD**: 단위 테스트는 비즈니스 로직을 빠르고 결정적으로 검증하고, 통합 테스트는 DB/API 등 경계의 실제 동작을 확인한다.
- **SHOULD**: 외부 서비스, 현재 시간, 난수, 네트워크에 의존하는 테스트는 가능한 경우 제어하여 재현 가능하게 한다.

## 3. 검증 절차

1. 변경에 관련된 **가장 좁은 테스트**를 먼저 실행한다.
2. 저장소에서 지원하는 린트·타입 검사·빌드 등 적절한 검증을 수행한다.
3. 가능하면 해당 영역의 회귀 테스트 또는 전체 테스트를 실행한다.
4. 오류가 발생하면 수정한 후 관련 검증을 다시 수행한다.
5. 실행 불가한 항목은 **미실행**으로 표시하고 차단 사유를 기록한다.

> 시간·환경·권한·외부 의존성 때문에 검증이 불가능한 경우, 이를 숨기지 않고 작업 보고서에 명시한다. 실제 서비스와 연결되는 테스트는 별도 승인 없이 실행하지 않는다.

## 4. 검증 결과 표준

| 상태 | 의미 | 보고 예시 |
| --- | --- | --- |
| PASS | 명령을 실행해 성공을 확인 | `unit tests: PASS (명령: ...)` |
| FAIL | 명령을 실행했으나 실패 | `lint: FAIL (원인: ...)` |
| NOT RUN | 실행하지 않음 | `integration: NOT RUN (테스트 DB 없음)` |
| NOT APPLICABLE | 변경과 관련 없는 검사 | `migration test: N/A (DB 미변경)` |

## 5. 금지 및 주의사항

- 커버리지 숫자를 임의로 만들거나 측정하지 않은 비율을 보고하지 않는다.
- 스냅샷을 무작정 갱신해 실제 회귀를 덮지 않는다.
- 테스트 픽스처에 실제 비밀 키나 개인정보를 사용하지 않는다.
- 성능 개선 주장은 필요 시 기존/변경 후 조건을 명시한 벤치마크로 검증한다.

## 6. 완료 기준

`docs/DEFINITION_OF_DONE.md`를 따른다. 테스트의 부재나 실행 불가를 이유 없이 묵살할 수 없다.
