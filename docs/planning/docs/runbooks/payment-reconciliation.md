# Runbook: 수동 입금 / PG 대사 불일치 대응 (v0.2)

- Owner: Payment BE owner + 운영 Lead / 범위: 최초 수동 입금 확인, 후속 PG Sandbox
- 현재 `confirm_order()`는 주문 상태만 변경하고 Payment 내역을 갱신하지 않으므로, **대사 Runbook은 To-Be 문서**다.

## 감지
주문이 `결제확인`인데 Payment 내역/입금 증빙이 없는 경우, PG 승인금액≠주문금액, 중복 승인/환불, 미확정 대기.

## 조치
1. 주문/거래 범위에서 추가 승인·반복환불·재시도 차단(관제·권한 있는 운영자만).
2. 주문ID·결제ID·PG 거래키·request_id로 감사로그와 외부 거래조회 확인(개인정보 로그 최소화).
3. 거래 원본 출처(수동 확인 vs PG 승인)를 구분하고 상태·금액·시간(영업일/결제일/정산일) 비교.
4. 중복/불일치 유형 분류 → 기존 멱등키·재처리 기록 확인 → 도메인 오너의 승인 후 재처리.
5. 거래 내역을 조용히 SQL UPDATE로 덮어쓰지 않으며, 원인·조치·정정 이벤트 보존.
6. 대사 재수행 → 수치/거래건수 검증 → 사용자/점주 알림 필요성 판단.

## 사후
발견 시간·영향 금액/건수·원인·임시완화·재발 방지 테스트·개발 변경/릴리즈 링크를 Incident로 기록한다.
