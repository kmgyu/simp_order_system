# 팀 개발·16주 로드맵 — v0.2

## 1. 인력 구성 / 실제 업무량
팀 4~6명, 주당 **개인별 약 6~10시간 가정**. 리더가 PM/Tech Lead/백엔드 핵심을 겸임해도 한 명에게 결제·인증·DB 리뷰가 모두 집중되지 않도록 분산한다.

| 역할 | 제안 인원 | 1차 책임 | 리뷰 교차 |
|---|---:|---|---|
| Product·Tech Lead/BE | 1 | 도메인 우선순위, Flask 유지 ADR, 핵심 불변식 | 다른 BE와 인증·재고 상호검토 |
| Flask BE | 1~2 | 주문/결제/재고 서비스·MySQL·pytest | FE 계약·DB 리뷰 |
| Vue FE | 1~2 | 기존 UI API 연결, 점주·고객 UX, E2E | BE와 명세 리뷰 |
| QA/Infra | 겸임 0.5~1 | Docker, CI, 배포, 로그, 백업/장애 실험 | 출시 게이트 독립 점검 |
| UX/운영 실험 | 전원 중 1명 오너 지정 | 점주 인터뷰, 파일럿/운영 교육 | 사용자 스토리 교차 |

최소 3명이라면 P1 멀티매장과 P2 PG·ERP 연동은 기본 일정에서 제외한다.

**변경 이유:** 이미 Flask 서버에 주문·캐셔·주방·서빙 API가 있으므로 "백엔드 신규 구축"이 아니라 "현재 데이터 정합성·권한을 복구하고 검증"하는 데 일정을 배정한다. 실제 파일럿 인원/매장 확보가 지연되면 모의 운영 후 지속 섭외; '실사용' 성공이라고 기록하지 않는다.

## 4. 개발·회의·코드리뷰 규칙
- 2주 Sprint, 매주 30분 동기회의 + 주 1회 10분 통합데모, Sprint 종료시 계획/회고 각 30~45분.
- 매일 회의 강요 대신 GitHub Project `Backlog / Ready / Doing / Review / Blocked / Done` 상태 공유.
- `main` protected, 기능 브랜치 `feat/<issue>-topic`, `fix/<issue>-topic`, `docs/...`.
- squash merge, PR 1인 이상 리뷰 승인 + 필수 CI. 인증·결제·재고·DB는 책임 오너 검토 필수.
- 모든 PR은 문제/기대값/변경 근거/테스트/스크린샷/API/스키마 영향/롤백/AI 사용 범위 기록.
- 위험한 DB 변경·보안 노출은 리뷰 이후에만 운영 반영. 운영 긴급 조치는 별도 hotfix 승인·사후 기록.
- 결정 충돌은 대안·비용·실험과 함께 ADR, 교착 시 Tech Lead 결론 및 재검토 조건.

## 5. Definition of Ready / Done
**Ready:** 대상 사용자 또는 기술 리스크 명확 / 현행 재현 여부 / 수용 조건과 비범위 / 담당·리뷰어·의존 이슈 / 테스트 계획.
**Done:** 정상·실패·보안·동시성(관련 영역) 자동 테스트 / DB 변경 migration/rollback / API 문서 / QA 실동작 / PR 승인 / 배포 증거. UI만 작동하면 Done 아님.

## 6. 출시 게이트(조건 하나라도 실패하면 공개 파일럿 보류)
- 익명/비인가 캐셔·재고·결제 변경 불가.
- 주문 중복/마지막 재고 동시성/취소 복원 자동 테스트 통과.
- DB 백업 **복원** 실제 시험 완료.
- debug·개발 secret·무제한 CORS 등 운영 설정 차단.
- 개인정보·주문 이력 권한·보유정책 확정.
- 운영 장애 대응자, 연락 방법, 배포 롤백·수동 주문 백업 프로세스 준비.
