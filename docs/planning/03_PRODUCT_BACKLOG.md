# 제품 및 기술 부채 백로그 v0.2

## 0. 우선순위와 관리 기준
`P0` = 안전한 파일럿 출시 차단 문제, `P1` = 점주 제품화·확장, `P2` = 심화 학습(정산/ERP), `P3` = 시장 확인 후. 각 Issue는 **사용자/위험→현행 코드→변경→Given/When/Then→테스트/배포 증거**를 적는다.

## C. 의존 관계
`T01`→`T02/T03/T04/T06`→`T05`→`T09/T12`→`F01~F05`→파일럿→`F06~F09`→`F11~F13`.
여기서 핵심 기능은 이미 존재하는 부분을 **신규 개발/개선/대체/검증**으로 표시한다. 예컨대 캐셔 UI는 신규 작성이 아니라 기존 Pinia 경로를 서버 API 호출로 바꾸는 작업이다.

## D. 주요 예외 시나리오
- 장바구니 가격이 바뀌면 최신 금액을 안내하고 확정 전 재동의를 받는다.
- 재고 한 건에 동시 주문 시 서버 잠금 또는 조건부 차감 적용, 실패 주문에는 재고 부작용 없음.
- 주문 생성이 DB 커밋되었으나 HTTP 응답이 유실되면 동일 키로 기존 주문 ID를 반환한다.
- 결제 성공·서빙 완료는 독립 상태; 취소 승인/환불 완료도 별도 이벤트로 추적한다.
- `StoreTable.updated_at`이 아니라 `table_session_id`로 현재/과거 주문을 판별한다.
- 점주 스타일 변경은 코드 편집이 아니라 안전한 토큰/미리보기/게시 프로세스를 따른다.

## E. 이슈 예시 (T02)
**Story:** 운영자로서 품절된 메뉴가 판매되지 않고 취소 시 재고가 정확히 복구되길 원한다.
**Given:** 메뉴 잔여 1, 다른 두 고객이 동일 메뉴 1개를 주문한다.
**When:** 요청이 동시에 들어온다.
**Then:** 한 요청만 성공; 재고 0; 실패 요청에는 주문이 생기지 않는다.
**그리고:** 성공 주문을 취소하면 재고는 1, 동일 취소 2회 후에도 1.
**증거:** pytest + MySQL 동시성 통합 테스트, DB 조회 캡처, 트랜잭션 경계 ADR.
