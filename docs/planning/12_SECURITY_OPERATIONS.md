# 보안·운영·파일럿 준비 계획 v0.2

## 1. 보안 As-Is 핵심 확인
- `run.py`: `app.run(debug=True, host="0.0.0.0", port=3000)` (개발 서버용, 운영 금지).
- `run.py`: `CORS(app)` 전체 적용(운영 허용 origin 제한 필요).
- `config.py`: `SECRET_KEY`가 없으면 `default-secret` 사용(운영에서 실패 처리 필요).
- 캐셔·메뉴 재고 수정·전체 주문 조회 등 라우트에 인증/역할 검증이 명시되어 있지 않음.
- `GET /order/payment_info/<id>` 등 주문 식별자 기반 조회는 주문 소유·세션 범위 검증 필요.
- 고객 FE는 전화번호를 입력하지만 현재 API 요청에는 실리지 않음. 불필요한 정보 수집을 피하기 위해 **수집 자체 필요성을 먼저 재검토**한다.

## 2. P0 보안 체크리스트
| 범주 | 구현/확인 과제 | 테스트 |
|---|---|---|
| 인증 | 점주/직원 로그인, 서버 세션·토큰 만료, 비밀번호 해시 | 익명 명령 API 401 |
| 인가 | 역할(Owner/Cashier/Kitchen/Server)별 최소권한 | 서버 403, UI 우회 허용 안 됨 |
| 주문 조회 | QR/주문 상태 토큰으로 해당 주문·테이블 회차만 접근 | 다른 주문 ID 열람 거부 |
| CORS/CSRF | 실제 허용 origin만, 쿠키 기반이라면 CSRF 보호 | 다른 origin/변조 CSRF 거부 |
| 설정 | Production debug=False, 설정 누락시 실행 실패, 비밀키/DB 계정 vault/env | debug 모드 외부 노출 불가 |
| 개인정보 | 전화번호 필수 여부, 최소수집·고지·파기/보유 기간·로그 마스킹 | 로그에 개인 식별값 없음 |
| DB | DB 계정 최소권한, TLS 및 백업 암호화, SQL 인젝션 검증 | 권한/쿼리/복원 점검 |
| 악용 | 관리자 변경 rate limit 및 audit, 고객 주문 과도요청 제어 | 부하·남용 요청 거절 |
| 외부결제 | 카드정보 저장 금지, PG 키는 서버에만, 웹훅 서명/출처 인증 | 위변조 웹훅 불수용 |
| 운영 | 취약 의존성/secret scan, 배포 승인, Incident owner | CI 경고 분류 기록 |

## 3. 로컬·스테이징·운영 환경
- 로컬: 두 저장소별 `.env.example`, Docker Compose API+DB+FE. **운영 실데이터를 로컬로 복제하지 않는다**.
- Staging: 익명화/합성 데이터, PG test key, 실제 환경과 동일한 DB major version/스키마.
- Production: HTTPS/reverse proxy, 전용 운영 계정, healthcheck, `debug=False`, secure secret, 명시 origin, 백업 스케줄 및 적어도 1회 복원.
- 프론트 번들에 서버 비밀키/결제 Secret Key 노출 금지. `VUE_APP_API_BASE_URL`는 공개해도 되는 API 주소만.

## 4. 운영 지표(초기 내부 관찰 기준)
- 주문 생성 요청 수, 성공/4xx/5xx, p50/p95, DB lock wait/deadlocks, 재고 예약 실패율.
- 결제/수동확인 대기 건수, 취소/환불/대사 불일치 건수, 주문 상태 처리 지연.
- SSE 활성 연결 수, 재연결 횟수, 이벤트 누락 진단 지표.
- 배포 버전+request_id+order_id+store_id(비밀 데이터 제거)로 이슈 역추적.
- 지표가 수집되기 전에는 "99.9% 가용" 등의 성과 수치를 약속하지 않는다. 관찰 후 SLO 설정.

## 5. 장애 대응 / 에스컬레이션
`발견 → 담당자 통보 → 고객 영향 범위 식별 → 위험 기능 제한(수동 주문/결제 전환) → 로그·DB 사실 확인 → 안전한 재처리 → 사용자/점주 안내 → 회고·회귀 테스트`.
- 주문 중복, 결제 중복/허위 승인, 무인증 관리자 접근, 복원 실패는 신규 개발을 중단하고 P0 대응.
- 실제 결제 상태 확인 없이 수동으로 `PAID` 설정하거나 DB UPDATE로 정산 금액을 맞추지 않는다.
- 실사용 파일럿 전 전자적 주문이 불가능한 상황을 대비한 종이 주문·현장 결제 전환 및 복구 시 재입력/중복 방지 절차 마련.

## 6. 배포 게이트
**아래가 하나라도 미완료면 대외 서비스 공개 불가:**
1. 인증·권한(P0)과 위변조 직접 API 테스트 통과.
2. 재고·취소·멱등 동시성 및 실패 롤백 자동 테스트 통과.
3. API 로그 개인정보 제거, 보유/삭제정책·이용자 고지 결정.
4. DB 백업·실제 복원 훈련, 이전 버전 배포·데이터 변경 대응.
5. 운영 Debug/CORS/Secret 설정, 보안 패키지 업데이트 및 서버 운영 방식 검증.
6. 파일럿 점주 동의, 상담/문제 대응 연락처·운영 책임자.
