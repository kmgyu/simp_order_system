# 프로젝트 헌장 (Project Charter) — v0.2

- Status: Draft / 문서 책임자: Product·Tech Lead / 기준일: 2026-10-14
- 기존 소스: [FE](https://github.com/Capybara-Clinic/mnu_pub_order_system), [BE](https://github.com/Capybara-Clinic/capybara-qr-order)

## 목적과 문제 가설
기존 학생 포차 QR 주문 시스템의 FE와 Flask BE를 출발점으로, 1개 소규모 식음료 매장에서 실제 주문·주방·서빙을 운영 가능한 제품으로 안정화한 뒤 소상공인 운영 SaaS로 확장한다. 핵심 성과는 **주문/결제/재고 정합성**과 **실서비스 운영 경험 및 팀 개발 절차**다.

- 가설 1: 행사·소형 매장에서 메뉴 변경, 품절 안내, 주문 누락·상태 확인의 비용이 크다.
- 가설 2: 기존 학생 포차 화면의 QR→주문→처리 기능을 재사용하면 파일럿까지의 시간을 단축할 수 있다.
- 검증 방법: 타깃 점주 3~5명 인터뷰(목표) 및 1개 파일럿(현재 확보되지 않음). 가설은 사실로 서술하지 않는다.

## 사용자/역할
| 역할 | 핵심 작업 | 인증 범위 |
|---|---|---|
| 고객 | 매장 QR→메뉴→주문→진행 조회 | 매장/테이블의 제한된 비회원 접근; 다른 주문 조회 금지 |
| 점주 | 매장 설정, 메뉴·재고·직원·매출 관리 | 본인 소속 매장만 |
| 캐셔/주방/서빙 | 결제 수동 확인, 조리, 서빙, 취소 요청 | 역할별 최소권한·감사 |
| 플랫폼 운영자 | 매장 지원/장애 관리 | 운영 행위 별도 감사 및 권한 승인 |

## 제품 범위
- **P0(실사용 안전)**: BE 구동·DB 초기화, FE 계약 정리, 주문/재고/취소 트랜잭션, 멱등키, 인증·권한, 테이블 이용회차, 최소 메뉴 관리, 테스트/CI, 배포·복원, 파일럿.
- **P1(점주 제품화)**: 공지문구/가격/메뉴/영업시간·배너/테마, 매출 CSV, 2개 매장 데이터 격리.
- **P2(심화)**: Mock PG/PG sandbox, 환불·대사, ERP용 CSV 및 API 어댑터.
- **P3(검증 후)**: 구독료 결제, 외부 POS, 복잡한 재고 BOM·회계, 플랫폼 지급대행.
- **제외**: 플랫폼이 구매대금을 직접 받고 여러 매장에 분배, 카드정보 저장, 법적 검토 없는 라이브 PG 연결, 사용 근거 없는 초대형 아키텍처.

## 공학 원칙
1. 가격·상태·수량·권한은 **서버 DB가 최종 검증**하고 클라이언트 상태는 UI용 캐시이다.
2. 주문/결제/서빙/재고 이동/테이블 세션은 별개 모델과 상태 전이로 취급한다.
3. 장애와 동시성은 운영 후 발견하지 말고 회귀 테스트로 선제 검증한다.
4. Flask/SQLAlchemy/MySQL 유지 A안을 우선 검토하고, 교체 비용을 명시한다.
5. 협업 문서(ADR·PR·Runbook·실험 보고서)도 코드와 함께 버전 관리한다.
6. 정산 합계는 주문 금액이 아닌 검증된 결제·환불 거래 기록에서 계산한다.

## 성공 지표(초기 목표; 수치 합의 필요)
- 정의한 테스트 환경에서 동시 주문에도 음수 재고·중복 생성 0건.
- P0 권한 교차 테스트(역할/다른 매장) 100% 통과.
- 직원과 점주가 핵심 흐름 1회 이상 실사용해 개선 사항 제출(실사용 전이면 계획으로만 기재).
- 서비스 장애·복원 리허설 1회, API/DB 변경 문서 및 PR 연결 100%.
- 응답시간·오류율·SSE 접속 수 등의 지표 수집(목표값은 베이스라인 측정 후 결정).

## 출시 금지 조건
인증 없는 캐셔/재고 변경, 금액·재고 불일치, 미검증 DB 백업, 실제 개인정보 처리 기준 미정, 지급·환불 테스트 미실시 상태에서 실서비스 공개 금지.
