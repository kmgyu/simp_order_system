# 도메인 불변식과 회귀·경쟁 조건 테스트 계획 (v0.2)

## 1. 원칙
테스트 통과 기준은 **API 응답만이 아니라 DB 최종 상태**다. 테스트는 실제 MySQL/MariaDB InnoDB 트랜잭션을 사용하고, 각 테스트 전 fixture를 격리한다. SQLite 메모리 테스트만으로 Row-lock 동시성 검증을 완료했다고 주장하지 않는다.

## 2. 불변식 정의
| ID | 불변식(항상 지킬 규칙) | 검증 데이터 |
|---|---|---|
| I01 | 유효 재고가 0 미만으로 확정되지 않음(유한 재고 상품) | `menus.stock_quantity`, inventory movements |
| I02 | 하나의 멱등키와 요청 해시는 주문 한 번만 확정 | `orders`, `idempotency_requests` unique |
| I03 | 실패한 주문은 주문·상세·재고 기록을 남기지 않음 | 거래 전후 DB 집계 |
| I04 | 주문 확정 시 단가/상품명 스냅샷은 이후 메뉴 변경에도 유지 | `order_items` snapshot |
| I05 | 주문 취소는 한 번만 재고 보정, 이미 차감된 내역만 보정 | 주문 상태, `inventory_movements` unique |
| I06 | 수동 결제 확인은 권한+상태+금액 검증 후 1회만 반영 | order/payment/audit/event |
| I07 | 누적 환불 승인 금액은 유효 승인 금액을 초과하지 않음 | payment/refund sums |
| I08 | `CANCELLED` 등 종결 상태는 허용 정책 없이 되돌릴 수 없음 | status history |
| I09 | 주문은 하나의 매장·테이블 이용회차에 귀속됨 | `orders.store_id`, `table_session_id` |
| I10 | 매장 A/직원 A가 매장 B/직원 B의 권한으로 데이터 조회/수정 불가 | 401/403/404, 감사로그 |
| I11 | 같은 외부 이벤트·ERP 매핑 작업은 중복 반영하지 않음 | unique(provider_event_id), integration job key |

## 3. 필수 재현/기대 테스트
| 테스트 | Given / When | Then |
|---|---|---|
| TC01 기존 재고 버그 | 재고 10, 3개 주문 후 취소 | 최종 10. 현재 코드에서는 주문 차감 없음+취소 증가 확인 대상 |
| TC02 마지막 1개 | 재고 1, 서로 다른 키 주문 2건 병렬 제출 | 정확히 1건 성공, 주문 1건, 재고 0 |
| TC03 중복 클릭 | 같은 멱등키/본문 20개 동시 요청 | 주문 1건, 응답은 동일 ID/충돌 규칙 일관 |
| TC04 멱등키 충돌 | 같은 키/서로 다른 상품 | 409, 최초 주문·금액 유지 |
| TC05 수량 검증 | 0, -1, 매우 큰 수량 | 4xx, 주문/상세/재고 변경 없음 |
| TC06 처리 중 오류 | 항목 1 저장 후 항목 2는 삭제/품절/예외 | 전체 rollback, 잔여 레코드 0 |
| TC07 메뉴 가격 변경 | 주문 직후 가격/이름 수정 | 주문 당시 금액/이름 스냅샷 불변 |
| TC08 중복 취소 | 주문 취소 2번 연속/병렬 | 재고 복원 1회, 주문 이력 보존 |
| TC09 상태 역전이 | `CANCELLED` 주문을 `PAID`/`SERVED`로 변경 | 409/422 정책 오류, 거래 불변 |
| TC10 결제 반복확인 | 동일 주문 수동 결제 확인 2번 | Payment 기록 1회 효과, 역할 검사 통과 |
| TC11 권한 우회 | 익명 사용자 `POST /menu/stock/update` 등 | 401/403, DB 값 불변 |
| TC12 테넌트 격리 | 점주A 세션으로 B의 order/menu ID 조회 | 정보 누출/변경 불가 |
| TC13 테이블 재사용 | 테이블 1회차 종료 후 새 2회차 시작 | 이전 주문이 새 회차 목록에 미등장, 과거 이력 보존 |
| TC14 SSE 재연결 | SSE 연결 끊김 후 주문 상태 변경 | 다시 연결 시 최신 상태를 조회/복구 |
| TC15 결제 콜백 유실 | PG 승인 성공, 애플리케이션 콜백 차단 | 미확정 기록 후 외부조회/웹훅으로 복구, 중복 승인 없음 |
| TC16 ERP 실패 | 주문 커밋 후 외부 ERP API 503 | 주문 성공 유지, outbox 재시도 및 기록 |

## 4. pytest 계층화(권고/아직 미구현)
- `tests/unit/`: 재고 계산 규칙, 합계·상태 전이 표, 요청 스키마.
- `tests/integration/`: Flask test client + **실제 InnoDB DB**, rollback, FK, Unique, 격리·락.
- `tests/contract/`: FE 요청과 OpenAPI 응답 shape, API 변경 감지.
- `tests/e2e/`: 브라우저 2대/2세션으로 고객 주문·관리자 확인·서빙.
- `tests/performance/`: Locust 또는 k6(선택), 주문 100 동시 요청은 성능 SLA가 아닌 **일관성 실험 조건**.

## 5. 실험 설계
- 자료: 메뉴 1개 재고 1, 테이블 2개, 멱등키 각기 다름, 별도 DB 커넥션과 동시 시작 장벽.
- 측정: 성공/409 개수, DB 주문건수, 재고 잔량, DB lock wait, deadlock 건수, p95.
- 성공조건: 성공 주문 1개 + 재고 0 + 실패 부작용 0. 20회 반복 후 로그/DB 결과 기록.
- DB 격리수준·커넥션풀·InnoDB 버전과 호스트 CPU를 실험 보고서에 함께 기록한다.
- 외부 API는 Mock/PG 샌드박스 응답을 변경해 허위 PAID, 타임아웃, 중복 이벤트를 반복한다.

## 6. 테스트 이행 단계
**Red** (기존 버그를 검증 가능하게 재현) → **Policy** (재고예약/차감 등 ADR) → **Green** (서버 트랜잭션) → **Refactor** (service layering) → **Regression** (CI 필수 테스트) → **Pilot** (모니터링).
