# 통합 고도화 프로젝트 계획서 v0.2 — 팀 공유용

초안
목적: 학생 포차용 실제 코드 2개를 보유한 팀이 소상공인용 주문·매장 운영 SaaS의 작동·검증·운영을 달성

## 1. Why / 제품 가설
교내 행사 주문 UI+Flask API를 재사용해 모바일 QR 주문, 점주 설정, 직원 주문처리, 판매·재고 이력을 안정화한다. 이 프로젝트의 차별화 포인트는 단순 화면 CRUD가 아니라 데이터 일관성, 상태 전이, 장애 및 복구, 협업의 품질이다. 실제 매장 운영자와의 인터뷰 전에는 시장 수요를 사실로 표현하지 않는다.

## 2. As-Is
- FE: Vue 3/Pinia/Vue CLI. 고객/캐셔/서빙 UI, SSE 수신 등 일부 HTTP 연동. 동시에 프론트 로컬 Pinia mock 데이터와 직접 상태 수정 로직이 존재.
- BE: Flask 3.1.1, Flask-SQLAlchemy 3.1.1, PyMySQL, MySQL 연결 문자열. Menu/Order/OrderDetail/Payment/StoreTable/Category/QRCode 모델 및 주문·메뉴·캐셔·주방·서빙 Blueprint 존재.
- 핵심 갭: 서버 권한 검증 부재, 주문 재고 차감 누락과 취소 재고 증가의 불일치, 주문-결제 상태 동기화 부재, 테이블 회차를 타임스탬프로 추정, SSE 폴링+ID 커서 한계, FE/BE API 계약 불일치, 자동 테스트/CI·마이그레이션 미확인.
- 검증 수준은 정적 코드 독해. 배포 경험·성능·실제 장애 발생 여부는 별도 검증한다.

## 3. To-Be / 16주 종료 모습
A. 실제 접속 가능한 1개 파일럿 매장의 `QR→메뉴→주문→캐셔→주방/서빙→매출 확인` 업무를 처리한다.
B. 서버가 금액과 재고의 원천이며 중복 클릭/동시 주문/재시도/취소에 대한 불변식 테스트가 있다.
C. 관리자·직원 권한, 데이터 이력, 감사 로그, 장애 탐지 및 백업 복원 방법이 있다.
D. 추가 심화: Mock 결제 및 대사, 테스트 PG, ERP CSV 중 P0 안정화 이후 가능한 것만 완성한다.
E. 팀 산출물: PR 리뷰·ADR·OpenAPI·ERD·테스트·부하/장애 실험 및 사용자 피드백 보고서.

## 4. 범위 조절
- P0: 기존 백엔드 실행/통합, 인증, 주문·재고/취소 정합성, 최소 점주 메뉴 관리, 배포·테스트, 1개 매장 파일럿.
- P1: 공지/스타일 변경, 매장 다중화·테넌트 격리, 주문 리포트, 권한 세분화.
- P2: Mock PG/PG sandbox, 환불·대사, ERP CSV·연동 워커.
- P3: 플랫폼이 판매대금을 수납·배분하는 지급대행, 실물 POS·세무 자동화, 복잡한 프로모션.
- 비범위: PG 직접 개발, 라이브 자금 정산 대행, MSA/Kubernetes를 학습 목적으로 선도입.

## 5. 우선 변경 결정
1. Flask 유지 기본안. Java/Spring 전환은 별도 ADR과 기능/운영 가치 비교 후에만 결정.
2. MySQL 계열 DB 유지 기본안. 스키마 버전 관리는 Alembic/Flask-Migrate 도입 후보.
3. 두 저장소 유지 + 개발용 통합 workspace/compose로 시작. 소유권·라이선스 확인 전 코드를 단일 저장소에 복사하지 않는다.
4. 주문과 결제와 서빙 상태를 분리하고, 서버 트랜잭션/멱등성을 기준으로 구현한다.
5. 점주가 직접 변경할 수 있는 메뉴/문구/테마는 제한된 입력·게시 모델로 구성한다.

## 6. 기술 학습 심화 주제
- 트랜잭션/락: 재고 1개에 고객 2명이 동시 주문, 취소와 주문 동시 실행, 부분 실패.
- DB: 인덱스 설계, N+1, DB 트랜잭션 격리 수준, migration, 실행계획, 배치 집계.
- 결제: 수동 결제 확인을 Payment로 일원화, 중복 승인 방지, 웹훅, 환불 누계, 내부-외부 대사.
- ERP: 외부 API 장애에도 주문 확정 유지, Outbox/재처리, CSV 중복 전송·버전 관리.
- 운영: 배포, 장애 주입, 로그, SLA가 아닌 내부 SLO(제안치) 측정, 백업/복원, RCA.
